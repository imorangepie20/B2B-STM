# 새 프로젝트 적용 절차

## 1. 복사

- [ ] `templates/AGENTS.template.md`를 새 루트의 `AGENTS.md`로 복사
- [ ] `docs/project-rules`, `docs/overview`, `docs/changes`, `docs/architecture`, `docs/business-logic`, `docs/decisions` 생성
- [ ] 현재 개발 상태와 변경 기록 템플릿 복사
- [ ] `harness-manifest.yaml`을 복사하고 placeholder 교체

## 2. 프로젝트 고유 항목 작성

- [ ] 프로젝트명과 한 문장 목표
- [ ] 사용자 역할과 핵심 업무 흐름
- [ ] 반드시 유지할 도메인 관계와 정합성
- [ ] 독립해야 하는 기존 프로젝트·DB·계정·배포 대상
- [ ] 참조 테마·디자인 자산의 원본 경로와 수정 허용 범위
- [ ] 기술 스택, 실행 포트, 개발·테스트 DB
- [ ] 완료 기준과 미검증 항목 표기 규칙

## 3. 스킬·플러그인 확인

- [ ] 현재 세션의 available skills에서 필수 스킬 확인
- [ ] harness와 designlang 플러그인의 실제 버전 확인
- [ ] 구조 시각화가 필요하면 `archify` 설치, 새 세션 노출, `doctor` 통과 확인
- [ ] 없는 스킬은 사용자 환경에 설치하고 새 세션에서 노출 확인
- [ ] 프로젝트에 필요 없는 플러그인은 설치하지 않음
- [ ] 외부 앱 연결은 필요한 권한과 데이터 범위를 확인한 뒤 구성

## 4. 검증 명령 정의

- [ ] unit/integration 테스트
- [ ] DB migration 반복·rollback·동시 실행 검증
- [ ] API live/readiness
- [ ] 브라우저 핵심 업무 E2E
- [ ] 데스크톱·모바일 viewport 캡처
- [ ] 운영 정합성 검사
- [ ] 백업·복원 리허설
- [ ] 빌드 또는 패키징
- [ ] Archify 다이어그램을 사용한다면 JSON `validate`와 최종 HTML `deliver`

각 항목이 프로젝트에 해당하지 않으면 삭제하고 이유를 기록합니다. 존재하지 않는 검증을 형식적으로 추가하지 않습니다.

## 5. 첫 작업으로 하네스 검증

- [ ] 에이전트가 `AGENTS.md`에서 지정한 문서를 순서대로 읽음
- [ ] 작은 기능 하나를 계획·테스트·구현·검증·문서화
- [ ] 기존 사용자 변경을 되돌리지 않았는지 확인
- [ ] 비밀값과 로컬 산출물이 Git에서 제외됐는지 확인
- [ ] 다음 세션이 `current-development-context.md`만 읽고 이어갈 수 있는지 검토

## 6. 하네스 유지보수

- [ ] 스킬·플러그인 버전 변경 시 manifest와 목록 갱신
- [ ] 같은 피드백이 반복되면 규칙이나 템플릿에 반영
- [ ] 존재하지 않는 파일·명령·스킬 참조 제거
- [ ] 완료된 다음 작업을 현재 상태 문서에서 정리
- [ ] 분기마다 백업 복원, 브라우저, 정합성 검증 명령 재실행
