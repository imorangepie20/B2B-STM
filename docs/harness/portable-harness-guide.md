# 하네스 구조와 운영 방식

## 목표

이 하네스는 여러 세션과 프로젝트에서 다음 행동을 일관되게 유지합니다.

- 작업 전에 현재 상태와 도메인 관계를 읽습니다.
- 기능 구현 전에 범위와 완료 기준을 명확히 합니다.
- 증상을 가리는 임시 수정 대신 원인을 수정합니다.
- 테스트, 실제 DB/API, 브라우저 화면을 변경 성격에 맞게 검증합니다.
- 의미 있는 변경은 다음 작업자가 판단할 수 있도록 문서화합니다.
- 참조 테마와 외부 도구는 제품 소스·비밀값과 분리합니다.

## 네 층 구조

### 1. 저장소 진입 규칙

루트 `AGENTS.md`에는 매 작업에 필요한 최소 규칙만 둡니다. 프로젝트 고유 업무 관계, 참조 자산, 독립해야 할 다른 시스템을 여기서 선언합니다.

### 2. 지속 문서

- `docs/project-rules/`: 바뀌는 빈도가 낮은 원칙과 문서 접근 순서
- `docs/overview/current-development-context.md`: 현재 구현 상태, 검증된 범위, 다음 작업
- `docs/architecture/`: 시스템 경계, 데이터 관계, 트랜잭션 원칙
- `docs/business-logic/`: 정상·예외 업무 시나리오
- `docs/decisions/`: 확정 사항과 선택 근거
- `docs/changes/`: 날짜별 구현 이유, 내용, 검증 결과
- `docs/superpowers/specs`, `docs/superpowers/plans`: 승인된 설계와 다단계 구현 계획

### 3. 환경 스킬과 플러그인

스킬은 작업 방법을 제공하고 플러그인은 스킬·MCP·앱을 묶어 제공합니다. 현재 세션의 사용 가능 목록을 기준으로 호출하며, 캐시 경로나 설치 상태를 프로젝트에 복사했다고 가정하지 않습니다.

### 4. 프로젝트 검증 명령

각 프로젝트는 실제 기술 스택에 맞는 짧고 반복 가능한 명령을 제공합니다. B2B-STM에서는 unit/integration, DB 정합성, API health, Playwright, 백업 복구 리허설을 분리했습니다. 새 프로젝트에서는 같은 명령명을 억지로 유지하지 말고 목적을 유지합니다.

### 5. 검증 가능한 구조 시각화

아키텍처·업무 흐름·sequence·상태 전이를 전달해야 할 때 `archify`를 조건부로 사용합니다. 확정 문서와 저장소 근거를 typed JSON 원본에 반영하고 `validate`와 `deliver` 영수증을 통과한 HTML/SVG만 공유합니다. 설치와 완료 기준은 [Archify 가이드](archify-guide.md)를 따릅니다.

## 표준 작업 흐름

1. 루트 `AGENTS.md`, 핵심 원칙, 문서 접근 순서, 현재 개발 상태를 읽습니다.
2. 관련 개요 → 아키텍처 → 업무 흐름 → 변경 이력 → 구현 파일 → 테스트 순서로 조사합니다.
3. 요구가 설계 선택을 포함하면 `brainstorming`으로 의도와 완료 기준을 정리합니다.
4. 여러 단계면 `writing-plans`로 파일·순서·검증을 기록합니다.
5. 기능·버그 수정은 실패하는 의미 있는 테스트에서 시작합니다.
6. 최소 범위로 구현하고 관련 테스트를 먼저 실행합니다.
7. UI는 실제 브라우저와 목표 viewport에서 기능·가로 넘침·정보 밀도를 확인합니다.
8. 완료를 말하기 직전에 최신 검증 명령을 다시 실행합니다.
9. 변경 기록과 현재 개발 상태를 갱신합니다.
10. 구조 설명이 복잡하면 Archify로 검증된 다이어그램을 만들고 원문 문서와 함께 연결합니다.

## UI 작업 흐름

1. 사용자가 지정한 참조 테마나 디자인 시스템을 원본 그대로 보존합니다.
2. 제품 코드로 필요한 토큰·컴포넌트·자산만 복사하고 출처와 허용 범위를 기록합니다.
3. 차트·데이터 그리드·달력·대화상자처럼 데이터 처리, 상태, 입력 또는 접근성 동작이 있는 UI는 검증된 라이브러리와 프로젝트 공통 컴포넌트로 구현합니다.
4. CSS·SVG·정적 마크업은 장식 표현에 사용하되, 기능성 컴포넌트의 외형만 재현해 구현을 대신하지 않습니다.
5. 라이브러리를 도입할 때 참조 테마와 기술 스택의 버전을 우선 확인하고, dependency를 고정한 뒤 production build로 호환성을 검증합니다.
6. `ui-styling`, `ui-ux-pro-max`로 반응형·접근성·업무 밀도를 점검합니다.
7. Playwright로 데스크톱과 모바일을 캡처하고 상호작용, console error, 실패 요청을 함께 확인합니다.
8. `designlang`으로 색상, 폰트, 간격, CSS 변수, WCAG와 화면 간 drift를 측정합니다.

## 데이터와 운영 작업 흐름

- 테스트 데이터, 데모 데이터, 운영 데이터를 명확히 구분합니다.
- 시드는 네임스페이스와 대상 DB를 검사하고 하나의 트랜잭션으로 처리합니다.
- 중복 요청과 동시 처리 검증은 DB 잠금·고유 제약·idempotency 결과까지 확인합니다.
- health 응답만으로 완료하지 않고 핵심 테이블과 업무 정합성을 확인합니다.
- 백업은 임시 DB에 실제 복원해 원본과 비교합니다.

## 문서와 실행 환경의 경계

- 저장소에 포함: 규칙, 버전, 설치 스크립트, 검증 명령, 비밀값이 없는 템플릿
- 저장소에서 제외: 토큰, 비밀번호, 세션 cookie, 로컬 도구 캐시, 분석 산출물, DB dump
- 새 프로젝트에서 교체: 프로젝트명, 도메인 관계, 참조 테마, 포트, DB명, 검증 명령, 배포 방식
