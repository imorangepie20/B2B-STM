# [PROJECT_NAME] 프로젝트 공통 작업 규칙

이 파일은 저장소 전체에 적용합니다. 하위 디렉터리에 `AGENTS.md`가 있으면 추가 지침도 함께 따릅니다.

## 작업 전 확인

매 세션 시작과 중요 변경 전에 다음 문서를 읽습니다.

1. `docs/project-rules/core-principles.md`
2. `docs/project-rules/doc-access-order.md`
3. `docs/overview/current-development-context.md`

구현·디버깅 전에는 프로젝트 개요와 현재 상태 → 아키텍처와 도메인 → 업무 흐름과 변경 이력 → 구현 파일과 테스트 순서로 확인합니다.

## 변경 원칙

- 증상 우회가 아닌 근본 원인을 수정합니다.
- `[DOMAIN_RELATIONSHIP]` 관계와 전체 업무 흐름에 미칠 영향을 확인합니다.
- 요청 범위에 필요한 최소 변경과 관련 검증을 수행합니다.
- 기존 사용자 변경과 작업 범위 밖의 코드를 수정하거나 되돌리지 않습니다.
- `[INDEPENDENT_PROJECTS]`의 코드·DB·계정·비밀값·배포 환경을 혼용하지 않습니다.
- `[REFERENCE_THEME_PATH]`은 참조 원본입니다. `[REFERENCE_THEME_POLICY]`에 따라 사용하고 비밀값과 내부 저장소 이력을 복사하지 않습니다.
- 차트·데이터 그리드·달력·대화상자처럼 동작과 접근성 계약이 있는 UI는 검증된 라이브러리와 프로젝트의 정식 컴포넌트로 구현합니다. CSS나 정적 마크업으로 외형만 흉내 내 완료 처리하지 않으며 데이터 연결·상호작용·키보드 접근·반응형 동작을 브라우저에서 검증합니다.

## 구현 흐름

- 설계 선택이 필요한 기능·UI 변경은 의도와 완료 기준을 먼저 정리합니다.
- 다단계 작업은 구현 계획을 문서로 남깁니다.
- 기능·버그 수정은 의미 있는 실패 테스트에서 시작합니다.
- UI는 실제 브라우저에서 데스크톱과 모바일을 확인합니다.
- 완료 보고 전에 최신 테스트와 검증 명령을 실행합니다.

## 문서화

- 의미 있는 아키텍처·업무·의사결정·구현 변경은 `docs/`에 기록합니다.
- 변경 이유, 근본 원인, 변경 내용, 검증 결과와 미검증 항목을 남깁니다.
- 일반 설명은 한국어로 작성하고 코드 식별자·경로·명령어·API endpoint·URL·환경 변수는 원문을 유지합니다.
- 검증하지 않은 기능을 완료로 표시하지 않습니다.
