# 첫 운영 버전 기준

작성일: 2026-09-05. 최종 갱신: 2026-09-09. 첫 운영 버전의 규모·권한·범위·검수 목표는 확정됐습니다. 핵심 업무와 로컬 운영 인수 스모크를 구현했고 목표 규모 본 시험과 실제 배포 검수는 남아 있습니다.
실제 도입 업체의 측정값이나 성능 보장이 아닌 개발 범위와 검수 목표입니다.

## 운영 모델과 규모

- 유통사 1곳, 창고 1곳. 여러 거래처가 같은 공급사의 포털을 이용합니다. 여러 유통사가 가입하는 SaaS는 첫 버전 범위 밖입니다.
- 거래처 100곳, 상품 1,000 SKU, 일 주문 300건, 주문당 최대 50개 품목, 동시 활성 사용자 30명을 검수 기준으로 제안합니다. 제품의 영구 제한값은 아닙니다.
- 규격별 SKU와 고정 포장 단위를 사용합니다. 박스·팩 등 SKU에 지정된 단위의 양의 정수 수량으로 거래하며 낱개 분할·복수 단위 환산은 제외합니다.
- 거래처별 단가를 지원하고 주문 당시 단가와 포장 정보를 보존합니다.
- 거래처 등록·사용자 초대는 관리자가 수행합니다. 공개 가입·자동 거래 승인은 제외합니다.
- 창고는 온라인 모바일 웹을 사용합니다. 연결이 끊기면 확정 완료로 표시하지 않고 복구 후 결과를 조회·재시도합니다. 오프라인 업무 확정은 지원하지 않습니다.

## 역할별 권한

| 역할 | 허용 업무 | 제한 |
|---|---|---|
| 거래처 사용자 | 소속 거래처 주문·취소·반품 요청, 단가·출고·정산 조회 | 다른 거래처 자료와 내부 원가·재고 정정 접근 금지 |
| 창고 담당자 | 입고·피킹·검수·출고, 반품 검수, 실사 결과 제출 | 거래 단가 변경, 반품 금액·마감·입금·권한 확정 금지 |
| 운영 관리자 | 거래처·상품·가격, 주문 확정·배정, 재고 정정·반품 금액 확정 | 정산·입금 권한은 별도 부여 |
| 정산 담당자 | 마감·조정, 입금·배분·환불 사실 기록 | 물리 재고·출고·사용자 권한 변경 금지 |
| 시스템 관리자 | 사용자 초대·차단·역할 부여, 감사 조회 | 업무 권한은 해당 역할을 별도로 부여 |

한 사람이 여러 역할을 가질 수 있습니다. 공유 계정 대신 개인별 계정으로 누가 확정했는지 기록합니다.
거래처 사용자는 첫 버전에서 하나의 거래처에만 소속됩니다. 내부 역할과 거래처 역할을 같은 계정에 혼합하지 않습니다.
메뉴 숨김뿐 아니라 API와 내보내기·첨부 접근에도 동일한 권한을 적용합니다.

## 포함할 업무와 경계

- 기본 공급처 등록과 입고 기록을 포함합니다. 구매 발주·매입 정산까지 확장하지 않습니다.
- 재고 실사는 창고가 수량·근거를 제출하고 운영 관리자가 정정을 확정합니다.
- 바코드 키보드 입력형 스캐너와 수동 상품 검색을 고려합니다. 카메라 인식·전용 PDA 연동은 후속 범위입니다.
- 출고 명세와 정산 명세의 인쇄·CSV 내보내기를 포함합니다. 법정 세금계산서 발행은 별도 연동 범위입니다.
- 상품·거래처·초기 재고·기초 미수·기초 미배분 입금의 가져오기와 검증을 포함합니다. 초기 잔액에도 기준일과 출처를 남깁니다.
- 이관은 미리보기·오류 행 안내·중복 실행 방지를 제공하며, 운영 개시 전 수량·잔액 대조를 통과해야 합니다.
- 확정 출고 후 운송 참조와 인도 완료 여부를 수동 기록합니다. 인도 기록은 중복 재고 차감이나 추가 청구를 만들지 않습니다.
- 다중 창고, 로트·유통기한, 배송 최적화, 은행·택배·회계 자동 연동은 후속 범위입니다.

## 성능과 안정성 검수 목표

반복 가능한 로컬 회귀 점검은 `npm.cmd run ops:acceptance-smoke`로 실행합니다. 현재 데모 데이터에 대한 짧은 스모크이며 아래 목표 규모와 30분 지속 부하 본 시험을 대신하지 않습니다. 실행 조건과 판정 방법은 [운영 인수 스모크 점검 안내](operational-acceptance-guide.md)에 기록합니다.

- 검수 데이터: 거래처 100곳, SKU 1,000개, 주문 100,000건과 주문 품목 1,000,000건. 출고·반품·정산 기록도 관계에 맞게 생성합니다.
- 부하: 동시 사용자 30명, 각 사용자 평균 3초마다 요청, 30분 지속. 조회 70%, 주문·출고·입금 등 변경 30%를 기준으로 합니다.
- 일반 목록·상세 API 응답 p95 1초 이하, 일반 변경 API p95 2초 이하를 목표로 합니다. 정상 요청의 예상 밖 서버 오류율은 0.1% 미만입니다.
- 월 마감·대량 가져오기·내보내기는 일반 요청 목표와 구분합니다. 진행 상태와 중복 실행 방지를 제공하고 상세 설계에서 처리량별 목표를 추가합니다.
- 같은 SKU에 대한 30개 동시 확정, 같은 작업의 10회 재전송, 확정 직후 응답 유실을 별도 재현합니다. 초과 배정·중복 원장·중복 청구는 0건이어야 합니다.
- 배포 환경 사양·DB 크기·네트워크 조건·측정 명령과 결과를 함께 기록합니다. 수치 통과 전에는 성능 달성을 주장하지 않습니다.

## 복구와 운영 검수

- 복구 목표 제안: 장애 시 최대 데이터 손실 15분 이내(RPO), 복구 4시간 이내(RTO).
- 배포 선택 시 이 목표를 충족할 백업·로그 보관·시점 복구 방식과 비용을 확인합니다. 일일 백업만으로 RPO 15분을 충족했다고 간주하지 않습니다.
- 별도 DB로 실제 복원하고 주문·재고·정산 원장과 참조 관계를 대조합니다. 복구 후 중복 요청 처리와 재개 절차도 검증합니다.
- API 오류, DB 연결 이상, 백업 실패, 정합성 이상을 탐지할 로그·상태 점검·알림을 마련합니다. 알림 채널은 배포 설계에서 정합니다.
- 운영 전 세 역할 화면의 정상·예외 시나리오, 모바일 360px 폭, 권한 우회, 세션 만료·통신 실패 복구를 검수합니다.
- 기초 데이터 대조, 관리자 계정 준비, 백업 복원, 장애 대응 문서, 미해결 결함 검토를 운영 인수 조건으로 둡니다.

## 남은 상세 설계

세금 포함 표시·반올림·지급 기한 기본값, 인증·초대 방식, 첨부 보관, 배포 비용과 복구 수단,
테마와 기술 스택, 대표 화면은 확정·구현했습니다. 배치·알림 작업 목표와 실제 배포 환경의 운영 수치는 아직 정해야 합니다.
