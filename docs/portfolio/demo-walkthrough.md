# 포트폴리오 데모 진행 순서

이 문서는 샘플 데이터가 준비된 로컬 환경에서 약 10분 동안 시스템의 핵심 업무 흐름을 설명하는 순서입니다. 계정 정보는 Git에서 제외된 `.demo-credentials.json`을 확인하며 문서에는 비밀번호를 기록하지 않습니다.

## 시작 전 점검

1. `http://127.0.0.1:3200/api/health/ready`가 200인지 확인합니다.
2. `http://127.0.0.1:3101`에서 로그인 화면이 열리는지 확인합니다.
3. 샘플 상태를 처음부터 보여줘야 하면 `npm.cmd run demo:reset`을 실행합니다.
4. `npm.cmd run ops:verify`로 테이블 수와 원장 정합성을 확인합니다.

## 1. 관리자 운영 현황

- `/admin`에서 주문, 출고, 매출, 반품, 재고, 정산 지표와 일별 순매출·상품별 출고 순위를 소개합니다.
- `/admin/orders`에서 샘플 주문을 선택해 주문 수량, 예약, 출고, 미확보 잔량이 별도 기록으로 유지되는 점을 보여줍니다.
- 재고 부족 주문은 추가 입고 뒤 미확보 수량만 재배정할 수 있음을 설명합니다.

## 2. 거래처 주문과 잔량 관리

- 거래처 계정으로 `/portal/orders`에서 계약 단가와 출고 창고를 확인하고 주문합니다.
- `/portal/orders/history`에서 부분 출고 후 주문량·출고량·남은 수량을 확인합니다.
- 미출고 잔량 취소와 원출고 수량 안에서만 가능한 반품 요청을 보여줍니다.

## 3. 창고 모바일 업무

- 창고 계정으로 `/warehouse/shipments`를 390px 폭 또는 실제 휴대폰에서 엽니다.
- 주문을 선택하고 품목별 이번 출고 수량을 입력해 부분 출고 화면을 설명합니다.
- `/warehouse/returns`에서 반품 실물을 정상·불량으로 나누고, 정상 수량만 판매 가능 재고로 돌아가는 흐름을 보여줍니다.

## 4. 재고와 반품 후속 처리

- `/admin/inventory-adjustments`에서 창고·SKU를 검색하고 실사 차이와 사유를 함께 기록하는 구조를 설명합니다.
- `/admin/return-credits`에서 검수 결과에 따른 차감 금액과 불량 보류·폐기 근거를 확인합니다.
- `/admin/audit-events`에서 주문 취소, 재고 정정, 반품, 정산, 계정 변경의 작업자·대상·사유를 검색합니다.

## 5. 정산과 입금

- `/admin/settlements`에서 출고 매출과 반품 차감으로 월 초안을 만들고 마감합니다.
- 마감 후 들어온 반품은 마감 자료를 수정하지 않고 다음 기간 조정으로 기록되는 점을 설명합니다.
- `/admin/payments`에서 입금 등록, 정산 배분, 취소와 재배분 이력을 확인합니다.

## 6. 운영 안전성 증거

- `/admin/accounts`와 `/admin/account-security`에서 역할, 계정 활성 상태, MFA 관리 범위를 소개합니다.
- [운영 인수 증빙](operational-acceptance-evidence.md)에서 권한 9/9, 원장 정합성 7개, 중복 요청과 동시 재고 검증 결과를 보여줍니다.
- [시스템 아키텍처](b2b-stm-architecture.html)에서 역할별 웹부터 NestJS transaction, PostgreSQL 원장까지 연결을 설명합니다.
- 관리자·창고·거래처 16개 화면의 데스크톱·모바일 Playwright 검증 32/32 결과와 대표 캡처를 보여줍니다.

## 데모에서 명확히 밝힐 범위

- 택배·은행·회계·전자세금계산서 자동 연동은 현재 범위 밖입니다.
- 성능 수치는 개발 DB의 로컬 스모크 결과입니다.
- 주문 100,000건·주문행 1,000,000건의 지속 부하 본 시험은 실행하지 않았습니다.
