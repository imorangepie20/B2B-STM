# 과도한 토큰 사용 보고서

작성일: 2026-09-09  
대상: 첨부 악성 파일 검사 구현부터 관리자 세션 만료 처리까지의 대화와 도구 실행

## 요약

이번 작업은 결과적으로 두 기능을 구현하고 오류 한 건을 수정했지만, 작업 규모에 비해 탐색·검증·리뷰를 여러 차례 반복해 토큰과 실행 시간을 과도하게 사용했습니다. 가장 큰 원인은 테스트를 많이 만든 것이 아니라 설계와 리뷰가 안정되기 전에 build·서버 재시작·검증을 반복한 점입니다.

정확한 입력·출력 토큰 수와 비용은 현재 세션에서 제공되지 않았습니다. 따라서 이 보고서는 확인할 수 없는 수치를 추정하지 않고, 대화 기록에 명시적으로 나타난 실행 횟수와 작업 패턴을 근거로 평가합니다.

## 확인된 과소비

| 구간 | 확인된 패턴 | 평가 |
|---|---|---|
| 초기 문서 확인 | 여러 프로젝트 문서와 긴 스킬 문서를 한 명령에서 전부 출력해 결과가 잘림 | 필요한 내용을 다시 읽게 만들어 중복 소비 발생 |
| 첨부 검사 구현 | API production build를 구현·통합·리뷰 수정·최종 확인 단계에서 총 4회 실행 | 중간 확인을 더 가벼운 TypeScript 검사나 집중 테스트로 대체할 수 있었음 |
| 세션 가드 구현 | Web production build 3회, 실행 중인 Web 교체 3회 | 리뷰 전에 서버를 교체해 후속 리뷰 수정 때 같은 절차를 반복함 |
| 코드 리뷰 | 첨부 검사 2회, 세션 가드 3회로 총 5번의 리뷰 응답 사용 | 보안 경계 검토 자체는 필요했지만 최초 요구사항과 권한표가 불완전해 재리뷰가 늘어남 |
| 샘플 데이터 진단 | PowerShell·Node 인용 오류, 존재하지 않는 열 조회 등 실패 명령 발생 | 실행 전 명령 검토와 기존 진단 스크립트 우선 사용이 부족했음 |
| 브라우저 확인 | DB와 인증 API에서 데이터 존재를 확인한 뒤 Windows 자동화 문서 전체를 읽고 연결 실패, 이후 별도 브라우저 스모크 실행 | `/admin`의 HTTP 401을 먼저 확인했다면 더 짧게 원인을 특정할 수 있었음 |
| UI 지침 검색 | Python 실행 가능 여부를 확인하지 않고 `python`, `py -3`를 차례로 시도 | 간단한 런타임 사전 확인으로 두 번의 실패를 피할 수 있었음 |
| 패치 적용 | 문맥 불일치와 존재하지 않는 `package.json` 줄을 대상으로 한 패치 실패 | 대상 줄을 먼저 좁게 확인하지 않아 재호출 발생 |
| 진행 설명 | 대부분 유용했지만 작은 단계마다 상태 설명이 추가됨 | 사용자에게 필요한 결정·위험·결과 중심으로 더 압축할 수 있었음 |

## 근본 원인

### 1. 검증 순서가 뒤집힘

세션 가드는 첫 build와 서버 재시작 후 코드 리뷰를 받았습니다. 리뷰에서 동시 요청 경합과 역할별 경로 정책 문제가 발견되어 다시 수정·build·재시작해야 했습니다. 설계 확인 → 정적 검토 → 단일 build → 단일 실행 검증 순서였다면 반복을 줄일 수 있었습니다.

### 2. 최초 권한 모델이 불완전함

`/admin` 전체를 하나의 관리자 역할로 취급했지만 실제 API는 `operations`, `settlement`, `system` 조합이 경로마다 다릅니다. 구현 전에 화면별 API와 역할 표를 먼저 만들지 않아 리뷰가 권한 불일치를 연속으로 발견했습니다.

### 3. 진단 종료 조건이 없었음

개발 DB에 DEMO 거래처 3개, 상품 12개, 주문 6개가 있고 역할별 API가 HTTP 200으로 데이터를 반환한 시점에 “데이터 삭제 아님”은 확인됐습니다. 그 뒤의 Windows 자동화와 전체 DEMO 브라우저 스모크는 사용자가 보고 있던 `/admin`의 인증 상태를 직접 확인하지 못하면서 비용만 추가했습니다.

### 4. 스킬 적용 범위를 넓게 잡음

필요한 절차 스킬을 따르는 것은 요구사항이지만, 모든 관련 가능성을 넓게 잡아 긴 지침을 읽고 검색 도구까지 실행했습니다. 특히 단순 인증 리디렉션 수정에서 UI 지식 검색의 실익은 작았고 Python 부재로 실패만 추가됐습니다.

### 5. 하나의 최종 검증 묶음이 없었음

코드 수정, 문서 수정, 리뷰 수정 직후마다 유사한 명령을 다시 실행했습니다. 최종 승인 후보가 된 뒤 build·집중 테스트·공개 저장소 검사를 한 번에 수행하도록 묶지 못했습니다.

## 필요했던 작업과 불필요하게 반복된 작업

필요했던 작업:

- 프로젝트 공통 규칙과 인수인계 확인
- 첨부 저장 전 ClamAV 검사와 fail-closed 처리
- 만료 세션의 보호 화면 차단
- 보안 경계에 대한 집중 테스트
- 변경 문서화
- 최종 production build와 실제 브라우저 리디렉션 확인

줄일 수 있었던 작업:

- 같은 대상의 production build 반복
- 리뷰 전 production 서버 재시작
- 이미 API로 확인된 데이터 존재 여부를 추가 도구로 재확인
- 긴 문서 묶음 출력과 잘린 결과 재조회
- 적용 가능성이 낮은 UI 검색 도구 호출
- 동일 리뷰어와의 다단계 재리뷰
- 오류가 예상 가능한 PowerShell 인용·경로 패턴 재시도

## 재발 방지 기준

앞으로 이 저장소에서는 다음 순서를 기본으로 사용합니다.

1. 인수인계와 대상 문서만 읽고, 관련 코드 검색 결과로 읽을 파일을 좁힙니다.
2. 구현 전 데이터 흐름 또는 권한표를 최대 10줄로 정리합니다.
3. 구현 중에는 가장 작은 정적 검사와 집중 테스트만 한 번 실행합니다.
4. 코드 리뷰는 production build와 서버 재시작 전에 한 번 받습니다.
5. 리뷰 수정이 끝난 뒤 production build를 한 번 실행합니다.
6. 실행 프로세스 교체는 최종 build 후 한 번만 수행합니다.
7. 최종 검증은 build, 집중 테스트, 공개 검사 순서로 한 묶음만 실행합니다.
8. 진단은 가설을 판정하는 증거가 확보되면 멈추고, 별개 문제는 기록만 합니다.
9. 외부 런타임을 쓰기 전에 `Get-Command`로 존재 여부를 확인합니다.
10. 진행 보고는 시작, 중요한 발견, 최종 검증의 세 시점 중심으로 제한합니다.

## 다음 작업의 토큰 예산 운영안

정확한 토큰 계측 기능이 없는 동안 다음 대체 지표를 기록합니다.

| 지표 | 목표 |
|---|---|
| production build | 기능당 최종 1회 |
| 실행 서버 재시작 | 기능당 최종 1회 |
| 집중 테스트 | 실패 재현 1회, 수정 후 1회 |
| 코드 리뷰 | 최종 후보 1회, 중요 결함이 있을 때만 재검토 1회 |
| 실패한 셸 명령 | 0회 목표 |
| 전체 회귀·시각·성능 검사 | 사용자 요청 또는 마일스톤 완료 때만 |
| 진행 메시지 | 결정·중요 발견·최종 결과 중심 |

## 결론

이번 과소비는 기능 복잡도 자체보다 순서와 종료 조건의 문제였습니다. 특히 “리뷰 전에 build·재시작”, “원인이 확인된 뒤 추가 진단”, “권한표 없이 공통 가드 구현”이 반복 비용을 만들었습니다. 다음 작업부터는 최종 후보가 안정된 뒤 한 번만 build·재시작·검증하고, 근거가 확보된 진단은 즉시 종료하는 방식으로 줄입니다.
