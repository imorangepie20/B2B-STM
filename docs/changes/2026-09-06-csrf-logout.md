# CSRF 보호와 로그아웃

## 이유와 구현

쿠키 인증의 변경 요청에 Origin·CSRF 검사가 없어 승인된 인증 설계의 요청 보호 경계가 미완성이었습니다. 전역 CsrfGuard가 SessionGuard보다 먼저 실행되어 공개 로그인도 보호합니다.

- `GET /api/auth/csrf`: no-store 응답으로 CSRF 토큰과 HttpOnly 쿠키를 발급합니다. 클라이언트는 JSON의 `csrfToken`을 메모리에 보관합니다.
- `POST /api/auth/login`: 쿠키와 `x-csrf-token`, 정확한 `Origin`이 필요합니다. 성공 후 이전 CSRF 쿠키를 지우므로 새 세션으로 토큰을 다시 받습니다.
- `POST /api/auth/logout`: 동일한 검증과 유효 세션 확인 후 현재 세션만 DB에서 폐기하고 쿠키를 지웁니다. 성공은 204, 재사용한 폐기 세션은 401입니다.
- 모든 변경 메서드에 Origin과 CSRF 검증을 적용합니다. GET/HEAD/OPTIONS는 변경 메서드 검증 대상에서 제외합니다. CSRF 발급 GET에도 Origin이 있으면 일치 여부를 검사합니다.
- `csrf-csrf@4.0.3`의 서명된 double-submit 방식을 사용하고 세션 쿠키를 서명에 연결합니다. 현재 자체 PostgreSQL 세션과 로그인 전 요청을 함께 지원하기 위한 선택입니다. 쿠키와 헤더가 일치해도 서명이 잘못되거나 다른 세션의 토큰이면 거절합니다.
- `cookie-parser@1.4.7`을 사용하되 중복 세션/CSRF 쿠키는 별도로 거절합니다.

라이브러리의 세션 연결·쿠키 설정 계약은 [공식 문서](https://github.com/Psifi-Solutions/csrf-csrf)를 확인했습니다. 이 라이브러리는 상태 저장 세션에 csrf-sync도 권장합니다. 본 변경은 기존 자체 세션 구조에 맞춘 서명 방식입니다.

## 환경 설정

- `APP_ORIGIN`: 경로나 마지막 `/` 없는 브라우저 출처. 개발 기본값은 `http://127.0.0.1:3100`이며 실제 터널에서는 발급된 HTTPS 주소로 설정하고 API를 재시작합니다.
- HTTPS 출처는 개발 모드에서도 Secure 쿠키를 설정합니다. CSRF 쿠키는 HTTPS에서 `__Host-b2b_csrf`, HTTP에서 `b2b_csrf`입니다. 세션 쿠키 이름은 `b2b_session`입니다.
- 운영은 HTTPS APP_ORIGIN과 최소 32바이트 난수의 hex 표현인 `CSRF_SECRET`이 필수입니다. 값은 Git 제외 환경 파일 또는 비밀 저장소에 보관합니다.
- 개발에서 키를 생략하면 프로세스마다 난수 키를 사용합니다. 재시작 후 토큰을 다시 받아야 합니다. 여러 API 인스턴스는 같은 키를 사용해야 합니다.

## 기존 실패 제한 보정

기존 테스트는 계정 없음 실패와 존재하는 계정 실패를 같은 IP로 합산해 이메일 제한의 경계값 오류를 놓쳤습니다. `> 5` 때문에 정확히 5회 실패한 계정의 다음 로그인도 허용됐습니다. 독립 이메일/IP와 실제 PostgreSQL 서비스 테스트로 재현한 뒤 `>= 5`로 수정했습니다.

테스트 정리는 전체 login_failures 삭제에서 이번 테스트의 키만 삭제하는 방식으로 변경했습니다. 이번 변경에는 DB migration이 없습니다.

## 검증과 남은 범위

2026-09-06 검증 결과: `npm.cmd run build:api` 통과, `npm.cmd run test:foundation` 10개 통과, docs 29개 파일 내부 링크 검사 통과. 참고용 `SDTPL_ADM` 내부 Git 상태에 변경이 없습니다. 실제 Cloudflare HTTPS 경유 브라우저 검증은 아직 수행하지 않았습니다.

CSRF·운영 설정·HTTPS 쿠키의 테스트 실패를 먼저 확인한 후 구현했습니다. 실제 DB와 HTTP로 위조 Origin, 누락/변조 토큰, 익명 토큰의 로그인 세션 재사용, 세션 간 토큰 교환, 중복 쿠키, 로그아웃 후 401과 다른 세션 유지, 이메일/IP별 여섯 번째 시도 차단을 검증합니다.

초대·비밀번호 재설정·MFA, 실제 웹 로그인 UI와 프록시 뒤 클라이언트 IP 신뢰 설정은 남아 있습니다. 현재 프록시 IP를 사용자 IP로 신뢰하도록 설정하지 않았으며 프록시를 통한 요청은 동일 IP 제한에 묶일 수 있습니다. Cloudflare 연결 전에 주소와 라우팅을 정해야 하며 이번 기록 시점에 터널은 시작하지 않았습니다.
