# 응답 유실·API 재시작 장애 주입 검증

작성일: 2026-09-10.

## 검증 이유

업무 transaction이 커밋된 직후 네트워크 응답이 사라지면 사용자는 성공 여부를 알 수 없습니다. 이때 API가 재시작되더라도 같은 `requestId`의 재전송이 새 주문을 만들지 않고 원래 결과를 반환해야 합니다.

## 검증 방식

- 테스트 DB에 격리된 거래처, 계정, 창고, 상품과 재고를 준비합니다.
- 일회성 TCP 프록시가 주문 요청을 첫 API 인스턴스에 전달하고 API의 첫 응답 바이트를 클라이언트에 전달하지 않은 채 연결을 끊습니다.
- DB의 `command_results`에서 주문과 결과가 커밋됐음을 확인합니다.
- 첫 API 인스턴스를 완전히 종료하고 같은 DB를 사용하는 두 번째 인스턴스를 시작합니다.
- 같은 계정, 본문과 `requestId`로 주문을 재전송합니다.
- 원래 주문 ID가 반환되고 `orders`, `order_lines`, `command_results`가 각각 한 건만 존재하는지 확인합니다.
- 검증 종료 시 테스트 레코드를 제거하며 개발 DB와 DEMO 데이터는 사용하지 않습니다.

## 결과

`npm.cmd run test:fault-recovery` 통과:

- 응답을 받지 못한 첫 요청의 transaction 커밋 확인
- API 인스턴스 교체 후 저장 결과 재생 확인
- 주문, 주문 품목, 명령 결과 중복 0건 확인

## 범위

이번 검증은 대표 상태 변경인 거래처 주문 접수를 대상으로 `command_results` 복구 계약을 확인했습니다. 프로세스 강제 종료가 transaction 중간에 발생하는 경우는 PostgreSQL rollback 성질과 기존 transaction 테스트 범위이며, 실제 배포 로드밸런서·네트워크 장애는 배포 환경에서 별도로 확인합니다.
