# 보호 업무 화면 세션 가드

작성일: 2026-09-09.

## 변경 이유

세션이 만료된 상태로 `/admin`에 직접 접근하면 대시보드 셸과 0건 지표가 먼저 렌더링되고, 각 API의 HTTP 401을 일반 데이터 로딩 실패로만 표시했습니다. 이 때문에 실제 DEMO 데이터가 남아 있어도 모두 사라진 것처럼 보였습니다.

## 근본 원인

API의 `SessionGuard`는 만료 세션을 정상적으로 HTTP 401로 거절했지만, Web의 `/admin`, `/portal`, `/warehouse` 레이아웃에는 자식 화면을 렌더링하기 전 세션과 역할을 확인하는 공통 경계가 없었습니다.

## 구현 내용

- 세 보호 레이아웃을 공통 `WorkspaceSessionGuard`로 감쌌습니다.
- `/api/auth/me` 확인이 끝나기 전에는 업무 셸과 자식 화면을 렌더링하지 않습니다.
- 세션 없음·만료와 역할 또는 관리자 MFA 조건 불일치는 `/`로 이동해 기존 로그인·MFA 흐름을 사용합니다. 관리자 경로는 API와 같이 운영, 정산, 시스템 역할 조합을 구분하고 계정 관리·보안은 시스템 역할로 제한합니다.
- 동시에 여러 재확인이 발생하면 이전 요청을 취소하고 최신 응답만 반영해 오래된 정상 응답이 401 판정을 되돌리지 못하게 합니다.
- 브라우저 창 포커스 복귀, 문서가 다시 보이는 시점과 60초 주기로 세션을 재확인합니다.
- 인증 서버 상태를 판단할 수 없는 5xx·네트워크 오류는 로그아웃으로 오인하지 않고 재시도 화면을 표시합니다.

## 검증 결과

- 변경 전: 미인증 `/admin` 직접 접근이 URL과 빈 관리자 대시보드를 그대로 유지하는 실패 재현
- `npm.cmd run build:web`: 통과
- `npm.cmd run test:auth-redirect`: 새 production Web에서 미인증 `/admin`, `/portal/orders`, `/warehouse/shipments`가 `/` 로그인 화면으로 이동하고 운영 역할의 시스템 전용 계정 화면 접근이 허용된 `/admin`으로 복귀
- 모바일 로그인 화면의 입력·버튼 접근성과 가로 overflow 검사 통과

장시간 전체 브라우저 회귀는 사용자 요청에 따라 실행하지 않았습니다.
